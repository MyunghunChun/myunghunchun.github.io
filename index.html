CASE 1 · 형상관리

Smart TV → StandbyMe 형상 분리

동시 개발은 허용하되 이미지 간 side effect를 구조적으로 차단

기존 TV 형상

TV Image
TV Feature Layer
BSP Layer

제안 / 구현한 구조

TV Image  |  StandbyMe Image
TV Feature Layer  |  StandbyMe SW Layer
BSP Layer (공통)

핵심 설계 원칙

  • 제품별 변경 영역을 독립 SW layer로 캡슐화
  • 공통 BSP / TV 영역은 공유하되 제품 전용 변경이 서로 침투하지 않도록 분리

결과 — 동시 개발 가능 + 이미지별 산출물 관리 용이 + 변경 영향 범위 명확화

구현 및 운영 가이드

Layer 생성만이 아니라 '변경이 들어왔을 때 어디까지 분리할 것인가'까지 정의

1. StandbyMe SW Layer 생성
  • 기존 BSP / TV Feature 구조는 유지
  • StandbyMe 전용 기능을 별도 layer로 수용
  • 제품 전용 recipe / configuration의 격리
2. Compile Branch 분리
  • recipe 구성 시 물리적으로 분리된 StandbyMe layer에 작성
  • StandbyMe용 컴파일 분기 구성
  • 공통 코드와 제품 전용 코드의 경계 정의
3. 기능 추가 Governance
  • 빌드 대상/산출물 관리 기준을 제품 단위로 정리
  • 개발자가 변경 위치를 예측할 수 있도록 가이드

기능 추가 시 체크 질문

단순히 기존 모듈에 코드를 넣는 것이 아니라:

  • ① 제품 전용인가?
  • ② 다른 이미지에 영향을 주는가?
  • ③ 독립 module로 분리 가능한가?

→ 필요 시 모듈화하도록 개발 가이드

Yocto layer는 단순 폴더 분리가 아니라 '제품 변형을 관리하는 형상 경계'로 활용
CASE 2 · 개발 효율성

Recipe Dependency Visualization

Build-time dependency는 전체 모듈 정보를 제공하지만, Runtime dependency 정보는 모듈별로 제공됩니다. 이를 분석하기 위해서는 통합된 데이터 모델이 필요했습니다.

Recipe A/B/C→pkgdata→Module A/B/C→pkgdata parsing→Unified JSON→HTML
핵심 아이디어: 개별 recipe가 빌드 시 생성하는 pkgdata를 수집 → 하나의 dependency dataset으로 통합 → 사람이 탐색할 수 있는 HTML로 변환

Build Integration & Output

매 빌드에서 자동 생성되어 플랫폼 구조 분석의 진입장벽을 낮춤

Build Integration

  • Yocto class 생성
  • Build process에 class 적용
  • 빌드에 포함된 recipe의 pkgdata 탐색
  • 필요한 dependency metadata 추출
  • JSON으로 통합
  • image artifact path에 결과 저장

Automation

개발자가 별도의 분석 명령을 실행하지 않아도 아래 결과가 자동으로 산출되도록 구성

Build→Dependency JSON→HTML Report

제공 정보 / 활용

  • ① 전체 Module List
  • ② Module 선택 → 해당 module이 필요로 하는 module 그래프
  • ③ Reverse Dependency → 해당 module을 필요로 하는 module 그래프
  • ④ Image별 결과 보존 → 빌드 산출물 기준으로 특정 이미지의 구조를 확인
목표: '의존성을 알고 싶다' → 소스/recipe를 뒤지지 않고 산출물의 HTML에서 바로 확인
CASE 3 · 트러블슈팅

Full Build 3시간+ 문제의 원인 추적

문제 현상 — 30분 이내가 정상인 일반 App 변경에서 3시간 Full Build가 발생함

  1. 현상 확인App 변경 시 Full Build 발생, 3h+ 소요
  2. 범위 축소3개 Chip Vendor 중 특정 대만 Vendor에서만 발생
  3. 가설 설정BSP 관련 변경이 상위 dependency를 재빌드시키는 것으로 가정
  4. 추적 시작BSP module이 아닌 BSP 영향이 큰 LSM부터 sstate cache 추적
  5. siginfo Diff정상 Build와 문제 Build의 signature metadata 비교
  6. Root CauseKernel 재빌드 확인 → Kernel recipe의 version dependency 발견
핵심: '풀빌드가 발생했다'에서 멈추지 않고 BitBake signature 변화의 시작점을 찾아 원인을 recipe 수준으로 축소

sstate / siginfo 기반 Root Cause

재빌드된 모듈을 dependency chain을 따라 역추적

LSM←App Change→Full Build→siginfo Diff→Version Dependency→Kernel Driver→Kernel Recipe

분석 방법

bitbake가 생성한 sstate signature metadata(siginfo)를 정상 Build와 비교하여 재빌드 trigger를 식별

전문가 관점

sstate cache 자체를 '결과'로 보지 않고 signature를 통해 '왜 cache가 무효화되었는가'를 추적

Chip Vendor별 Kernel Build 차이 발견

동일한 BSP 계열이라도 vendor의 kernel packaging 방식 차이가 빌드 안정성에 영향을 줌

일반 Chip Vendor

Kernel Driver→Build Time Compile→Kernel / Driver Artifact

전체 Image Version 변화가 driver 산출물 이름에 직접적인 재빌드 trigger로 연결되지 않음

문제 Chip Vendor

Kernel Driver→사전 빌드된 .ko 사용→Recipe에 추가

문제: .ko 파일 naming에 전체 Image Version이 포함

→ Image Version 변경 → Kernel signature 변화 → Kernel 재빌드 → 상위 dependency 연쇄 재빌드 → Full Build

조치: Kernel recipe에서 불필요한 Version dependency를 무시하도록 처리하여 개발 Build의 Full Rebuild trigger 제거
CASE 4 · 재현성 / 환경

AirPlay 이상동작과 glibc 산출물 차이

Recipe version은 같았지만 실제 binary artifact가 달랐던 문제

  1. 초기 단서AirPlay 담당 개발자가 glibc 버전 문제 가능성을 확인. 정상 glibc를 적용하면 AirPlay 정상 동작 → glibc library가 핵심 용의자
  2. Version 검증정상 Branch vs 문제 Branch의 glibc recipe version 비교 → 동일. 동일 환경으로 재빌드 시 문제 재현 안 됨 → Recipe version만으로는 설명 불가
  3. Artifact 비교문제 build에서 생성된 glibc library를 직접 확보해 일반 build artifact와 비교 → 일부 .so의 SONAME / SO version 차이 발견
  4. Build Server 추적Build 기록으로 문제 artifact의 server 식별. 인도 Server 확인 → Host glibc가 문제 artifact와 일치. 한국/인도 환경 차이 확인

최종 Root Cause: Recipe + Host Environment

단일 원인이 아니라 두 문제가 결합된 재현성 문제

Root Cause #1 — Recipe 결함

Native glibc를 사용해야 하는데, Native module recipe가 build host의 glibc가 아니라 Host 환경의 library를 참조할 수 있는 구조였음.

→ 이슈 등록 및 후속 수정 대상으로 분리

Root Cause #2 — Build Server Drift

한국 / 인도 Build Server의 Host 환경이 동일하지 않음. Problem Build에서는 실제로 Host glibc를 사용했고, 그 차이가 artifact에 반영됨.

→ 즉각적으로 Build Server 환경을 일치시키는 조치

왜 여기서 멈추지 않았는가

'서버가 달라서 문제'가 아니라 '왜 서버가 artifact에 영향을 줬는가'까지 확인

Application: AirPlay→Runtime Artifact: glibc .so / SONAME→Recipe: native glibc dependency→Build Host: Host glibc
분석 관점: Version → Artifact → Build Log → Server → Recipe → Host Dependency 순으로 내려가며 원인을 분해
Artifact 검증Build 재현성Host 표준화
